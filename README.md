# Machine Kanbun（機械漢文）— Issue #1 検証基盤

LLM に渡す文脈を「漢字 + 漢文的省略 + 構造記号」の擬似漢文 IR に変換し、
トークン数・意味保持・TTFT がどう変わるかを測る。

## 構成
- `machine_kanbun/model.py` — 構造化 Fact / Question / Profile
- `machine_kanbun/encoder.py` — KCR エンコーダ。L0〜L5 と JSON を生成
- `machine_kanbun/data/profiles.json` — ベンチマーク(3 プロファイル / 49 facts / 47 問)。否定(不無未非禁)・時制・条件・因果・比較・数値・不確実性を含む
- `machine_kanbun/tokens.py` — トークナイザ比較(tiktoken。HF は任意)
- `machine_kanbun/lmstudio.py` — LM Studio(OpenAI 互換, ストリーミング)クライアント。TTFT とモデル実測の prompt_tokens を取得
- `machine_kanbun/qa.py` — プロンプト構築と採点(yes/no は先頭語、span は必須語/禁止語)
- `machine_kanbun/cli.py` — `tokens` / `qa` / `report`(Pareto frontier 付き) / `longqa` / `longreport`
- `machine_kanbun/gen.py` `legend.py` `longrun.py` `longreport.py` — Issue #4 長文評価(後述)
- `machine_kanbun/ablate.py` `ablreport.py` `convcost.py` — Issue #10 L1 アブレーションと変換コスト(後述)

```bash
python3 -m machine_kanbun tokens                       # オフライン・トークン比較
python3 -m machine_kanbun qa --model qwen/qwen3-8b     # 凡例なし(ゼロショット)
python3 -m machine_kanbun qa --model qwen/qwen3-8b --legend   # 演算子の凡例つき
python3 -m machine_kanbun qa --model google/gemma-4-12b
python3 -m machine_kanbun report
```

## 結果(temperature 0, 47 問 × 7 形式, 思考オフ)

### qwen/qwen3-8b
文脈のみのトークン(`results/tokens.txt`, o200k): L0 649 → L1 -46% / L2 -49% / L3 -49% / L4 -36% / L5 -49% / JSON +58%。

QA 精度(凡例なし → 凡例あり):

| 形式 | 精度 | 精度(凡例) |
|---|---|---|
| L0 自然日本語 | 100% | 100% |
| JSON | 93.6% | 93.6% |
| L1 日本語要約 | 91.5% | 91.5% |
| L2 漢字圧縮 | 93.6% | 93.6% |
| L3 擬似漢文 | 91.5% | 89.4% |
| L4 構造漢文 | 89.4% | 93.6% |
| L5 機械漢文 | 87.2% | 91.5% |

所見:
1. 文脈トークンは L2/L3/L5 で約 -49%(目標 -30% 達成)。JSON は逆に +58%。
2. ただし **L1(普通の日本語要約)も -46%** で、トークン効率は漢文系とほぼ同じ。漢文化の上乗せ効果はこのデータでは見えない。
3. 否定(不・無・未・非・禁)は全形式でほぼ満点。懸念されていた否定の区別は問題にならなかった。
4. 弱点は**不確実性(疑)**: L1〜L5 は 0〜33%。モデルが「疑」を答えとしてそのまま出力してしまう。L0 は 100%。時制も凡例なしの L4/L5 で劣化。
5. 精度 95% 維持の条件は、L1〜L5 のいずれでも未達(L0 との差 6〜13pt)。ただし 47 問・1 モデルなので 1 問 = 2.1pt。誤差が大きく、確定的な結論ではない。
6. TTFT は全形式で約 1.0 秒でほぼ同じ。1 リクエスト約 240〜470 トークン中、固定のシステム/指示部が約 175 を占め、短い文脈では差が出ない。TTFT 改善の検証には長い文脈(数千トークン以上)が必要。

### google/gemma-4-12b(`reasoning_effort: none`)
| 形式 | 精度 | 精度(凡例) | 文脈込み prompt tok/問 | vs L0(凡例なし) |
|---|---|---|---|---|
| L0 自然日本語 | 100% | 100% | 292.0 | 0% |
| JSON | 97.9% | 97.9% | 445.2 | +52.5% |
| L1 日本語要約 | 95.7% | 95.7% | 213.6 | -26.9% |
| L2 漢字圧縮 | 95.7% | 100% | 217.0 | -25.7% |
| L3 擬似漢文 | 97.9% | 100% | 219.7 | -24.8% |
| L4 構造漢文 | 97.9% | 100% | 246.0 | -15.7% |
| L5 機械漢文 | 95.7% | 100% | 218.4 | -25.2% |

### モデル比較の所見
1. gemma-4-12b は全形式で qwen3-8b より高精度。凡例ありなら L2〜L5 が 100% で、「精度 95% 維持 + 文脈トークン削減」を満たす。凡例なしでも L3/L4 が 97.9%、L2/L5 が 95.7%。
2. qwen3-8b が全滅した不確実性(疑)は、gemma では凡例ありで 100%、凡例なしでも 67%。漢字演算子の解釈力はモデル差が大きく、「漢字圏データを多く学習したモデルほど有利」という仮説をこの 2 モデルだけでは支持も否定もできない(qwen の方が中国語コーパスは多いはずだが結果は逆)。
3. 凡例(約 60〜90 トークン)は精度を上げるが、この短い文脈では節約分をほぼ食う(L2〜L5 の削減が約-25% → 約-6%)。凡例は固定費なので、文脈が長くなれば相対的に小さくなる。長文脈での再評価が必要。
4. 依然として L1(日本語要約)が L2〜L5 とほぼ同じトークン量。漢文化の独自の利点は、精度面(凡例あり)以外では確認できていない。
5. TTFT は両モデルで形式間の差がほぼない(約 1.4〜1.6 秒、ノイズ範囲)。短い文脈では測れない。
6. 1 問 = 2.1pt、各形式 47 問のため、差の多くは誤差範囲。

## Issue #4: 長文コンテキスト評価 (2k〜32k)

`Model × Representation × Legend × Context length` の4軸で評価。完全版は [results/long_report.md](results/long_report.md)、
生データは `results/long/*.jsonl`、演算子別プロファイルは `results/model_profiles.json`。

```bash
scripts/run_long.sh [model...]        # 再開可能。LM Studio が固まったら自動で再ロードして再開
python3 -m machine_kanbun longqa --model google/gemma-4-12b --lengths 2000 8000 --variants L1 L5:none L5:minimal
python3 -m machine_kanbun longreport
```

- 生成器 `gen.py`: 人物/案件/催事を乱数生成し、同一 facts から全形式を出力。文脈長は L0 の o200k トークン数で定義(圧縮形式はその結果として短くなる)。
  問題は意味カテゴリ別に層化し、**横断推論**(案件→担当者→職業、催事間の定員比較)と**参照解決**(愛称)を含む。48 問/文書。seed 固定で決定的。
- 形式: JSON / L0〜L5 / **Adaptive**(`data/policies.json` のモデル別方針で fact の種類ごとに圧縮度を変える)。
- 凡例: none / full(約62 tok) / minimal(`疑`のみ, 約14 tok) / category(質問カテゴリの演算子のみ, 約10 tok)。
- 計測: 文脈トークン(モデル実測 − 空文脈基準)、各変種1問目を**コールド**(prefix cache 無効化)として TTFT/prefill、2問目以降を**ウォーム**として別計上、
  実効凡例コスト(凡例tok / 再利用回数 R)と損益分岐、メモリ差分(best-effort)、L1 との対応あり符号検定、Pareto frontier。

### 結果 (gemma-4-12b, 各セル 48 問)
| 変種 | 2k | 8k | 16k | 32k | 文脈tok(8k) | vs L0 |
|---|---|---|---|---|---|---|
| JSON | 94% | 92% | ctx超過 | - | 9754 | +44% |
| L0 | 100% | 96% | 96% | - | 6794 | 0% |
| L1 日本語要約 | 100% | 98% | 94% | 96% | 3085 | -55% |
| L3 凡例なし | 100% | 100% | 98% | - | 3177 | -53% |
| L5 凡例なし | 100% | 100% | 94% | 92% | 3135 | -54% |
| L5 + minimal | 100% | 100% | 96% | 92% | 3135 | -54% |
| L5 + full | 100% | 100% | 98% | 92% | 3135 | -54% |
| Adaptive + minimal | 100% | 100% | 96% | 92% | 3135 | -54% |

### 所見(誤差を踏まえた結論)
1. **MKW は L1(日本語要約)と統計的に区別できない。** gemma で L1 との差は全変種で p ≥ 0.07(符号検定。JSON のみ L1 より悪い方向)。
   トークン量は L5 が L1 より約 2〜3% 多く、精度も同等。**このデータでは「漢文化」独自の利点は示せていない。** 一方で L0 比 -54% のトークン削減と、L0 と同等の精度は確認できた。
2. **TTFT は文脈トークンに比例する。** prefill は約 100 tok/s で長さによらずほぼ一定(gemma)。L0 比 TTFT は約 -55%(16k: 144 秒 → 63 秒)。ただしこれは L1 でも同じで、MKW 固有の効果ではない。ウォーム(キャッシュ命中)の TTFT は約 2〜4 秒で形式差なし。
3. **凡例は精度を有意に改善しなかった。** 16k で L5 の full が +4.2pt、minimal が +2.1pt だが 1〜2 問差。L1 より短くならないため、L1 比の損益分岐は常に「回収不能」。L0 比では 1〜8 facts で回収できるが、それは L1 でも得られる削減。
4. **Adaptive は固定 L5 に対して利得なし**(同一トークン量、精度も同等)。方針は issue 例の手設定で、モデルの Operator Profile から学習したものではない。
5. **32k で L5 系が L1 より約 4pt 低い**(92% vs 96%)が、差は 2 問(p は有意でない)。L5 系 3 変種は同じ問題を落としており、独立な証拠ではない。落とした問題は否定(無)2・因果1・横断推論1。
   「駐車場有」を「ない」と読むなど、`無`/`有` の取り違えが見られた。
6. **JSON はトークンが +44%、精度も最低**(92〜94%)。16k では gemma の実効コンテキスト(19456)に収まらなかった。
7. **演算子別**: 不・未・非・禁・疑・若・過今将 は L2〜L5 でほぼ 100%。弱いのは 無(83%, L5)、故(82%, L5)、`>`(86%)。qwen(2k のみ)の `疑` は各変種 n=3 で 0/3〜3/3 とばらつく(L1・JSON・adaptive は 0/3、L0・L5 凡例なしは 3/3)。n が小さく、`疑` 固有の弱点とも MKW 固有の弱点とも結論できない。

### 制約・未達(正直な記録)
- **qwen3-8b は 2k のみ。** 8k 以降は LM Studio がキャッシュ命中リクエストで「prompt processing 98.8%」のまま固まる事象が再現し(再ロード 5 回でも)、16k は Metal の GPU メモリ不足(16GB 機)で失敗した。失敗は `results/long_report.md` に記録。**モデル間の長文比較は未達。**
- 4k / 64k は未実施。32k は全文(L0/JSON)が実行不能(prefill > 15 分、コンテキスト超過)のため圧縮形式のみ。16k は 8 変種に絞った。
- gemma の実効コンテキストは `-c 36000` 指定でも 19456 だった(qwen は 20000 で読み込み)。
- メモリ/KV: LM Studio は API を提供しないため、RSS とシステム使用量の差分のみ。ばらつきが大きく**比較には使えない**。
- 数値・属性の正誤は部分文字列一致。同一文書の問題を全変種が共有するため、変種間の誤りは相関している。
- `則` 演算子は未実装。QA は生成データ(テンプレート由来)で、語彙・文型の多様性は限定的。
- 実験は gemma の凡例なし/ありを含め seed 1 の 1 文書/長さのみ。seed 間のばらつきは未評価。

## Issue #10: L1 アブレーション(LLM に必要な最小言語構造)

L1(日本語要約)から言語要素を**1つずつ**変換し、どこで精度が落ちるかを測る。完全版は [results/ablation_report.md](results/ablation_report.md)
(圧縮例・全表)、[results/ablation_table.csv](results/ablation_table.csv)、グラフ(SVG)は `results/ablation_pareto_*.svg`。

```bash
scripts/run_ablation.sh qwen/qwen3-8b 2000 1          # model lengths seed [variants]  (既定: 27 変種)
python3 -m machine_kanbun convcost --model google/gemma-4-12b --llm-lengths 2000 8000
python3 -m machine_kanbun ablreport
```

### 操作(`machine_kanbun/ablate.py`)と issue の梯子の対応
| issue | 操作 | 内容 |
|---|---|---|
| L1a 助詞削減 | `particle` | 助詞(は が を に の で と へ も より から)を除去。`ではない` は保護 |
| L1b 主語省略 | `subj` | L1 は既に主語を1度しか書かない。逆に**主語を全 fact に反復**して効果を測る |
| L1c 丁寧・語尾 | (未実装) | L1 に丁寧語尾が無く、変換対象がない |
| L1d 時制 | `tense` | 以前/現在/将来 → `過:` `今:` `将:` |
| L1e 属性統一 | `attr` | `1972年生まれ` → `生:1972` |
| L1f 漢字置換 | `kanji` | 小さな閉じた語彙で正書法のみ置換(コーヒー→珈琲, うどん→饂飩 ...) |
| L1g 語順固定 | `order` | 関係先頭 `好:鍋` `不飲:酒` |
| L1h operator | `simple` `neg` `unc` `cond` `cause` `cmp` | 意味クラスごとに漢字核/演算子へ(`疑:` `若A→B` `A故B` `好:A>B`) |
| (追加) | `struct` | `group{...;...}` 構造化 |

独立版(`ab=particle` など13種)と累積の階段版(`abL=` 11 段)を用意。**全意味演算子 + struct は L5 と文字単位で一致**する(テストで保証)。

### 圧縮例(同じ人物, o200k トークン)
```text
L1 (110 tok): 人物石田：1972年生まれ。職業は医療。…酒は飲まない。レバーは食べないらしい(未確認)。…以前はXperia。現在はSurface。将来はKindleを使う予定。Kindleは未購入。雨なら散歩に行かない。…
particle (L1 から助詞削除): 人物石田：1972年生まれ。職業医療。…酒飲まない。レバー食べないらしい(未確認)。海山好き。…雨なら散歩行かない。…
L5 機械漢文 (98 tok): 人物石田{生:1972;職:医療;住:名古屋;愛称:ヨシ;食{鍋好;酒不飲;疑:レバー不食;好:山>海};医{夜間珈琲禁};機{過:Xperia;今:Surface;将:Kindle;Kindle購入未};習{雨?散歩不行;残業過多故体調悪化}}
```
全表現の実例(L0〜L5, JSON, Adaptive, 各アブレーション)は `results/ablation_report.md` の冒頭にある。

### 結果
実施範囲: **qwen3-8b 2k × 2 seed(各 48 問, 27 変種)**、**gemma-4-12b 8k × 1 seed(22 変種)**、変換コスト。

1. **単独の変換で L1 と有意に違うものはない**(p ≥ 0.51)。95%CI は ±5〜9pt 程度で、**この規模で検出できるのは概ね ±5pt 以上の差**。「差がない」ではなく「検出できない」。
2. **トークン面で効くのは助詞削除だけ**(L1 比 -9%, 両モデル。精度は同等)。否定/不確実の演算子化は -3〜4%、時制 -0〜3%、他の意味演算子は ±1%、**構造化 `{}` は +6%、主語反復は +70% で精度利益なし**。累積しても最大 -13〜-17% で、**L1 は既に最小に近い**。
3. **漢字置換は効かない**(トークン +0.4〜0.9%、精度 +1〜2pt で有意でない)。H2「漢字化そのものの効果は小さい」と整合。うどん→饂飩のような稀な漢字は逆にトークンを増やす。
4. **構造化・演算子化の精度利益も示せなかった**。H3「L3/L5 の利点は構造化」は支持も棄却もできない(`struct` 単独は qwen で +1.0pt、累積の 11 段目では +3.1pt だが、いずれも有意でない)。
5. 傾向(有意でない, 探索的): qwen の累積 7 段(不確実→`疑:`)で -3.1pt、`order`(関係先頭語順)で -3.1pt(特に否定(無) `無:駐車場`)。gemma の 8k では全変種が L1 の ±2pt 内。
6. **トークン削減はトークナイザ依存**: 同じ文書で L5 の L1 比は o200k で -8%、qwen 実測 -5%、**gemma 実測 +1.6%**(`results/ablation_report.md` の表)。
7. **変換コスト**(gemma, L0 を LLM で L1 風に要約): 2k で 68 秒・8k で 221 秒、変換結果で QA 精度 100%(48 問)。変換結果を
   **約 6 回再利用**すれば時間で元が取れる(token 換算は出力を同価で約 3 回、5 倍重みで約 7 回)。ルールベース描画は 32k でも 2ms 未満だが、**構造化 facts が既にある前提**で、生文からの抽出コストは含まない。
8. **最小表現の候補**: 助詞削除(L1 比 -9%, 精度同等)。それ以上の圧縮は精度が落ちない確証が取れていない。

### 制約・未達
- 受け入れ条件のうち **2k/8k/16k/32k の全長比較は未達**。gemma の 2k は天井(L0/L1 とも 100%)で差が出ないため 2 変種のみで停止、16k/32k はアブレーションでは未実施(時間)。qwen は #4 の LM Studio 不具合で 8k 以降が測れない。
- 1 文書/seed。qwen 2k は 2 seed、gemma 8k は 1 seed(n=48)で検出力が低い。追加 seed でさらに絞れる。
- 合成データ(テンプレート由来)で語彙・文型が限定的。`particle`/`kanji` は閉じた語彙向けの単純ルールで、一般の日本語には使えない。
- 「語順固定」は関係先頭への並べ替えのみ。L1c(丁寧・語尾)は未実装。
- 変換コストは gemma のみ・各長さ 1 回。LLM 変換結果の QA は 48 問。T_saved は構造化 L1 との TTFT 差で近似(LLM 変換後の文脈は 949 tok と、構造化 L1 の 863 tok よりやや長い)。
- メモリ/ピーク使用量は #4 同様、比較に使える精度ではない。

## Issue #11: 多言語(EN/KO/JA)→ 共通 MKW

同一の Canonical Facts から EN/KO/JA の L0・L1 と MKW を生成して比較(`i18n.py` `mlenc.py`)。**MKW は関係・演算子・概念語を漢字(言語非依存)に統一し、
固有名詞(人名・愛称・都市・会場)だけ原言語の表記**を保つ。完全版は [results/ml_report.md](results/ml_report.md)(3言語の実例・全表)、[results/ml_table.csv](results/ml_table.csv)、`results/ml_pareto_*.svg`。

```bash
scripts/run_ml.sh                      # 本格実行(再開可能, 約3.3時間)
python3 -m machine_kanbun longqa --model google/gemma-4-12b --lengths 2000 --variants EN-L0 KO-MKW EN-MKW@JA --out results/ml
python3 -m machine_kanbun mlconv --model google/gemma-4-12b --length 2000   # 各言語の文 → MKW を LLM で直接変換(日本語を経由しない)
python3 -m machine_kanbun mlreport
```

### 同じ人物の3言語 × MKW(抜粋)
```text
EN-MKW: 人物Ishida{生:1972;職:医療;住:Nagoya;愛称:Yoshi;食{鍋好;酒不飲;疑:レバー不食;好:山>海};…}
KO-MKW: 人物이시다{生:1972;職:医療;住:나고야;愛称:요시;食{鍋好;酒不飲;疑:レバー不食;好:山>海};…}
```

### 所見
1. **MKW のトークン数は言語にほぼ依らない**: 3言語の変動係数は MKW 0.8〜1.1%、L1 8〜13%、L0 12〜18%(o200k・gemma・qwen のどれでも)。L0 は言語で大きく変わる(2k 相当 gemma: EN 1717 / JA 1899 / KO 2296)のに対し MKW は 879〜901。
   ただし**これは設計上の帰結**(概念・演算子を漢字に正規化し固有名詞だけ残す)で、LLM が自力でそう変換した結果ではない。
2. **精度は言語依存で、MKW が L1 に勝つ言語は無い**。MKW − L1(文脈長プール, 対応あり): gemma は JA ±0pt、EN **-5.7pt**(0/11, p<0.01)、KO -1.6pt(p=0.51)。qwen(2k)は KO -16.7pt(p=0.01)、EN -4.2pt。
   日本語以外では「MKW = 日本語要約相当」とは言えない。
3. **英語での低下の主因は「不確実性」**: EN-MKW の不確実性は 45%(L1 は 100%)。`疑:` を凡例なしで英語文脈から読めず、`疑:生卵不食` をそのまま「確定」と答える。不確実性を除くと EN-MKW の誤答は 7/181、EN-L1 は 2/181。#4 の知見(凡例が不確実性に効く)と整合する。**凡例を付けた条件は未測定**。
4. **質問言語の効果は無い**: 日本語固定質問(`@JA`)と同言語質問の差は ±2pt 程度で符号も一定しない。低下は質問言語ではなく**文脈の表現**(漢字 IR + 原言語の固有名詞)に由来する。
   (注意: `@JA` では「石田」↔「Ishida」の固有名詞対応も必要で、純粋な言語固定ではない。)
5. **トークン削減率は言語で違う**(gemma 8k, L0 比): MKW は JA -54% / EN -49% / KO -61%、MKW の L1 比は JA +1.6% / EN +5.6% / **KO -10.7%**。cold TTFT は KO で L0 85 秒 → MKW 35 秒(-59%)。韓国語では MKW のトークン優位が最も大きい。
6. **直接変換(各言語の文 → MKW, 日本語を経由しない)**: gemma 2k で 61〜69 秒・出力約 900 tok。正解 IR との項目 F1 は JA 0.72 / EN 0.52 / KO 0.45 と**言語順に低下**(固有名詞表記の一致を要求する厳しい指標)。変換結果での QA 精度は JA 98% / EN 88% / KO 90%(正解 IR では 100 / 96 / 96%)。
   変換結果を再利用すれば元が取れる回数: 時間で約 5〜7 回、token で約 3〜4 回(出力 5 倍重みで約 5〜8 回)。**8k の EN/KO は出力が上限 8000 tok に達して打ち切られ**(`results/ml_report.md` に明記)、数値は参考値。

### 制約・未達
- **1 seed・各セル 48 問**。差の多くは誤差範囲(95%CI は ±4〜10pt)で、有意なのは上記の gemma EN と qwen KO、全言語プールのみ。
- **採点を 3 回修正した**(英語・韓国語の否定表現、概念語の自由な訳「医療→Medical」、英語の月名・韓国語の同義語)。保存済み回答は全て最新の採点で再計算したが、**直接変換の QA 精度は回答が未保存のため旧採点**で、過小評価の可能性がある。比較問題(`好:A>B`)は答えに両方の語が含まれても正解にする緩い判定。
- 英語・韓国語の文は手書きテンプレート(合成データ)で、語彙・文型は限定的。自然さは未検証。
- qwen は #4 の LM Studio 不具合のため 2k のみ。gemma の 32k は全文(L0)が実行不能(全言語でコンテキスト超過)で圧縮形式のみ。
- **未実施**: EN/KO/JA の L1 → MKW、ルールベース/形態素解析/小型 LLM による変換との比較、言語横断 QA(文脈と質問の言語が異なる全組合せ)、#10 の L1 アブレーションとの統合、凡例あり条件。

## Issue #17: ラベル局所化(漢字共通語彙は何に効くか)

同一の骨格を3つの語彙で描画して比較(`irlabel.py`)。**IR-C**=共通漢字ラベル(現行 MKW と文字単位で一致)、**IR-L**=構造語・概念語を入力言語の単語に(日本語は IR-C と同一)、
**IR-ID**=構造語を言語共通の意味のないコード(`K1` `O1` `R3` …)に(名前・名詞・数値は IR-L と同じ)、**IR-IDL**=IR-ID + コード対応表(システムプロンプトに1回)。
完全版: [results/ir_report.md](results/ir_report.md)、[results/ir_table.csv](results/ir_table.csv)、`results/ir_pareto_*.svg`。

```text
EN IR-C : 人物Ishida{生:1972;職:医療;住:Nagoya;愛称:Yoshi;食{鍋好;酒不飲;疑:レバー不食;…}}
EN IR-L : Person Ishida{born:1972;occupation:healthcare;residence:Nagoya;nickname:Yoshi;food{hot_pot like;alcohol not drink;uncertain:liver not eat;…}}
EN IR-ID: E1:Ishida{K1:1972;K2:healthcare;K3:Nagoya;K4:Yoshi;G1{hot_pot R1;alcohol O1 R2;O7:liver O1 R3;…}}
```

```bash
scripts/run_ir.sh                       # 再開可能(約2時間: gemma 2k〜32k + qwen 2k, 8 変種)
python3 -m machine_kanbun irreport
```

### 言語間トークン CV(3言語の標準偏差/平均。主要指標)
| 計測 | IR-C | IR-L | IR-ID |
|---|---|---|---|
| o200k(2k〜32k) | 0.8〜0.9% | **8.1〜8.3%** | 3.0〜3.3% |
| gemma-4-12b 実測(2k〜32k) | 1.0〜1.1% | **9.6〜9.8%** | 2.9〜3.4% |
| qwen3-8b 実測(2k) | 0.8% | **10.2%** | 3.4% |

### 精度(EN+KO を比較。括弧外は gemma 2k〜32k プール、qwen は 2k)
| 条件 | gemma EN / KO | 対 IR-C(gemma, EN+KO) | qwen EN / KO | 対 IR-C(qwen, EN+KO) | 凡例 tok |
|---|---|---|---|---|---|
| IR-C | 93 / 95% | - | 92 / 81% | - | - |
| IR-L | 92 / 93% | -1.8pt (p=0.26) | 85 / 90% | +1.0pt (p=1.0) | - |
| IR-ID | 67 / 60% | **-30.7pt** (p<0.01) | 56 / 46% | **-35.4pt** (p<0.01) | - |
| IR-IDL | 85 / 79% | -12.2pt (p<0.01) | 73 / 56% | -21.9pt (p<0.01) | 215〜255 |

### 所見
1. **H2(漢字が共有中間語彙として安定性を生む)を支持**: ラベルを各言語の単語に戻すだけで、言語間 CV は IR-C の約 1% から約 10% へ**約 10 倍**に悪化する(o200k・gemma・qwen の全計測で一致)。構造が同じでも語彙が違えばトークン数は揃わない。
   IR-ID の CV(約 3%)は IR-L より低いが、これはコードが言語共通で、残る差は名前・名詞・単位の言語差による。
2. **局所化しても精度はほぼ変わらない**(IR-L − IR-C: gemma -1.8pt、qwen +1.0pt、ともに有意でない)。漢字ラベルは**トークンの安定性には効くが、理解精度には効かない**。一方で IR-L は IR-C よりトークンが多い(gemma 8k: EN +8.6%、KO +23%)ため、**IR-L は L1 比でも EN +15% / KO +10% 長く**、圧縮上の利点を失う。
3. **H3(ラベルの意味が精度に寄与)を強く支持**: 意味のないコードにすると精度が約 -31〜-35pt 崩れる。**否定(不)は 0%、未 10%、禁 21%、時制 55%**(gemma, EN+KO)。演算子の意味を取り出せないと、構造が同じでも理解できない。
   しかも IR-ID は**トークンも IR-C より約 25〜31% 多く**(gemma 8k: 3910 / 4085 / 4228 vs 3135 / 3170 / 3219)、トークンでも精度でも IR-C に支配される。
4. **凡例で一部回復するが戻りきらない**: 凡例(215〜255 tok, 文脈の約 5〜6%)で gemma +18.6pt、qwen +11.1pt 回復するが、IR-C には gemma -12pt、qwen -22pt 届かない。コード→意味の対応をゼロショットで引くのは苦手で、否定(不)は 54%、(非)は 50% にとどまる。
5. **例外: 不確実性**: IR-C 64% に対し、IR-L の `uncertain:` は **23%**(EN+KO, n=22)。各言語の語より漢字 `疑` のほうが「未確認」として解釈されやすい。n が小さく、語の選び方に依存する可能性がある。
6. **MKW の「言語非依存性」の再解釈**: 観測された安定性は**トークン数の安定性であり、漢字という共有語彙が担っている**。意味理解は漢字を LLM が既に知っていることに依存する(IR-C と IR-L の精度は同等)。構造だけでは言語非依存にならず、**非漢字圏言語で同じ効果が出るかは未検証**。

### 制約・未達
- 1 seed・各セル 48 問。差の多くは誤差範囲で、有意なのは IR-ID と IR-IDL の低下、凡例の回復のみ。
- 日本語の IR-L は IR-C と同一語彙のため再実行していない(比較は EN+KO)。qwen は #4 の LM Studio 不具合で 2k のみ。
- IR-ID は**構造語だけ**を抽象化(名前・名詞・数値は残る)。IR-L の語の選び方(`uncertain` `so` `not_yet` 等)は一つの実現で、別の語選びで結果が変わりうる。凡例は質問言語のみ。
- 中国語・ドイツ語・フランス語などの非漢字圏言語、IR 変換時間・E2E は未実施。

### 三層分解(gemma 8k, 同一 facts)
| 層 | 操作 | トークン変化 JA / EN / KO | 精度変化(長さプール, 対応あり) |
|---|---|---|---|
| 1 | L0 → L1(自然言語の簡潔化) | -55% / -51% / -57% | gemma -0.2pt, qwen +0.7pt(**不変**) |
| 2 | L1 → IR-L(各言語語彙のまま構造化) | +2% / **+15%** / **+10%** | gemma **-5.5pt**(p<0.01)、qwen **-9.4pt**(p=0.01) |

- **圧縮の大半は層 1(文法的冗長性の除去)で得られ、精度を損なわない**。課題文の整理は支持される。
- **層 2(構造化)はトークンを減らさず(EN/KO では増える)、精度を有意に下げる**。MKW が L1 に精度で劣る原因は漢字ラベル(層 3)ではなく**構造化記法そのもの**。構造化の価値はトークンではなく機械処理・正規化の側にある。
- 層 3 は精度に影響しないが、トークン面は言語依存(韓国語で最大 -19%、日本語は定義上 0)。

### 複数トークナイザ(Qwen3 / Gemma2 / Llama-3.1 / Mistral-Nemo / DeepSeek-V3 / o200k / cl100k, `tokenizers` で実測)
- **言語間トークン CV**: IR-C は全トークナイザで **0.6〜1.5%**、IR-L は 4〜21%、IR-ID は 1.4〜11%。共通ラベルによる正規化はトークナイザに依らない。

- **英語は割れる**: IR-C が IR-L より短いのは Gemma2(-10%)・DeepSeek(-5〜-6%)、長いのは o200k・Qwen3・Llama(+4〜+6%)、cl100k では +42%。
- L0 → L1 の削減は全トークナイザで -48〜-61% と頑健。

### ラベル種別(内容語は IR-L に固定し、構造語だけを変える。下表は gemma の値で、各族が測れた長さ(2k〜32k)の平均。qwen 2k も同傾向)
| 族 | 言語間 CV | トークン(対 IR-L) | 精度差(対 IR-L, EN+KO) |
|---|---|---|---|
| IR-C 漢字(構造+内容) | 0.8〜1.1% | -13% | +1.8pt |
| IR-CS 漢字構造語 | 3.2〜3.6% | -5% | -2.1pt |
| IR-EN 英語構造語 | 3.4〜4.2% | -5% | -0.5pt |
| IR-L 各言語 | 8.1〜10.2% | 0 | 0 |
| IR-ID 抽象 ID | 2.9〜3.4% | +13% | **-28.9pt** |
| IR-SYM レア記号 | 2.2〜2.9% | **+29%** | **-29.7pt** |

1. **CV を下げるのは「言語共通の構造語彙」で、漢字固有ではない**: 構造語を共通化すると CV は約 8% → 約 3.3%(漢字でも英語でも同じ)。さらに内容語(概念名詞・職業・単位)まで漢字に共通化すると 3.3% → 0.8%。#17 の「漢字が共有語彙」は「共通の構造語彙(文字種は問わない)」に修正すべきで、漢字固有の効果は内容語の共通化に限られる。

### コア意味プリミティブ(段階 B)と自然文(段階 C/D)
- `core.py` に **27 演算子**(極性 4・モダリティ 5・時制 5・認識 4・論理 3・比較 2・事象状態 3・自由記述の退避口 1)を `core-1.0` として凍結。関係・名詞は開いた語彙で、演算子で表せないものは `~"…"` に逃がし、その率をカバレッジ指標とする。
- `natural.py` / `natural_data.py`: 生成器とは独立に書いた **30 文 × 4 言語**(10 現象 × 3)で、**原文から直接** IR を作り(日本語を経由しない)、(a) IR のみで QA、(b) IR → 自然文の往復で QA、(c) 原文で QA(上限)を比較する。
**結果**(30 文 × 4 言語、各モデル 212 問。完全版: [results/synthesis/natural_report.md](results/synthesis/natural_report.md))

| 文脈 | gemma-4-12b | qwen3-8b |
|---|---|---|
| 原文(上限) | 99.5% | 94.8% |
| IR のみ(演算子の凡例なし) | 78.8%(-20.8pt, p<0.01) | 71.7%(-23.1pt, p<0.01) |
| **IR + 演算子の凡例** | **93.9%**(-5.7pt, p<0.01) | **84.0%**(-10.8pt, p<0.01) |
| 往復(IR → 自然文) | 89.2%(-10.4pt) | 81.1%(-13.7pt) |

1. **IR のみの精度が低い主因は情報の欠落ではなく、演算子の意味が読めないこと**: 凡例(約 250 トークン)を付けるだけで gemma +15.1pt、qwen +12.3pt。本当の情報損失は gemma で約 6pt、qwen で約 11pt。#4・#10・#17 で見た「凡例が効く」と一致する。
   (当初の「IR のみ」と「往復」の比較は、往復のプロンプトにだけ演算子の意味表が入っている混同があり、凡例つきの条件を追加して切り分けた。)
2. **往復は IR+凡例より低い**(gemma 89.2% vs 93.9%): 自然文への再生成で誤りが加わる(例: 過去の出来事の続きに `今` を付けて「現在〜する」と書き戻す)。IR は LLM に読ませる中間表現として、自然文に戻すより直接使うほうが情報を保つ。
3. **現象別(gemma, 凡例つき)**: 否定・不確実性・意図/中止・因果・条件は 100%、時制 96%、様相 96%、伝聞 90%。弱いのは**比較 70.8%** と**照応 83.3%**。
   比較は凡例でも改善しない。原因は記法と変換の曖昧さで、`>` が演算子位置ではなく内容中に置かれ、「新型は旧型より軽い」を `新型 > 旧型 重量` と書いて(重量が上=重い)**向きが反転**する、「太郎は次郎ほど速くない」で次郎が花子に置き換わる、など。**core-1.0 の比較は設計の見直しが必要**(形容詞+向きで符号化)。
4. **コアのカバレッジ(段階 B)**: コア演算子だけで表現できた変換は gemma 98%(117/120)・qwen 96%(115/120)、自由記述フォールバックは 1% / 1%。**27 演算子で 10 現象の自然文を実用上カバーできた**。未使用の演算子は gemma で `願` `>` `=`、qwen で `非` `確`(`>` は演算子位置ではなく内容中に置かれるため、パーサ上は未使用)。コア外の出力は書式の揺れ(`>=` `==` `將` など)が大半で、パーサの別表記として吸収した。
5. **言語差は小さい**: IR のみ 77〜81%(gemma)、凡例つき 92.5〜96.2%。日本語を経由しない直接変換が 4 言語で同程度に働く。
6. 短い文では IR のトークンは原文と同等(JA 1.00、EN 0.99、KO 1.13、ZH 1.51)。ここでの IR の価値は圧縮ではなく、**現象(否定・時制・不確実性・伝聞など)を明示して取り出せること**。変換は 1 件約 3 秒(gemma)。

### 制約
- L1 は決定的テンプレート要約で、LLM の要約ではない(層 1 は良いテンプレートの上限)。1 seed・各セル 48 問で、差の多くは誤差範囲。qwen は #4 の LM Studio 不具合のため 2k のみ。
- 中国語の語彙・文・質問は私が手書きしたもので、母語話者による検証はしていない。英語・韓国語も同様に手書きテンプレート。
- トークナイザ横断はオフラインのトークン数のみ(精度は gemma/qwen の 2 モデル)。Gemma2 は gemma-4 のトークナイザとは別物で、gemma-4 の実測とは数値が異なる(例: KO の IR-C vs L1 は gemma2 -21%、gemma-4 -11%)。
- 自然文は 30 文・各 1 回で小規模(現象あたり 3 文)。QA は文字列一致と極性語による機械採点で、人手評価はしていない。IR 生成と QA は同一モデル。
- core-1.0 は方針どおり凍結したままで、比較の設計見直しは次版(core-1.1)の課題。
- 未実施: 原文の形態素解析器による L1、複数モデルファミリでの精度、非漢字圏の他言語(独・仏)。

## Issue #20: 日本語 L0 と既存解析器ベースの簡易 L1

日本語の会話文だけを対象に、**L0(自然文のまま)**と、**既存の形態素解析器・係り受け解析器 + 軽量ルールで作る簡易 L1**を比べた。LLM も新しい解析器も使わない。全結果は [results/jp/report.md](results/jp/report.md)(表・変換例・グラフ)、[results.csv](results/jp/results.csv)、各 JSON/JSONL。

- 解析器: SudachiPy(モード C)、MeCab(fugashi + unidic-lite)、Janome(IPAdic)、GiNZA(spaCy, UD)。
- 簡易 L1 の変種: **m** 内容語と助動詞→標識(ない/た/らしい/たい/かも/みたい/う)に写像し、助詞・丁寧語・フィラー・敬語・形式名詞を削る(空白区切り)、**g** m を空白なしで連結、**p** 格助詞を残す、**d** GiNZA の係り受けで節に分け省略された主語を補う、**naive** 解析器なしでひらがな連を削るだけ(対照)。
- データ: 会話体メモリ生成器(`machine_kanbun/jpdata.py`)。状態 7 種(完了/未完了/予定/希望/未決定/伝聞/可能性)、主語省略・指示語・丁寧/口語・雑談混じり、最大 55,632 件。例: 「田中さんは会社を辞めた？」に対し、メモリが「迷っている・まだ決めていない」なら正答は「未確定」。
- コード: `jl1.py`(変換器)、`jpdata.py`、`jpbench.py`(実験1)、`jpretention.py`(実験4)、`jprag.py`(実験3)、`jpllm.py`/`jprun.py`(実験2・5)、`jpbreak.py`(実験6)、`jpretime.py`(埋め込み速度の再計測)、`jpstats.py`(符号検定)、`jpreport.py`。テストは `tests/test_jl1.py`。

### 主な結果

**1. 変換コストは無視できる(実験1)** 1 通あたり Sudachi/MeCab 約 0.05〜0.07 ms(約 2 万通/秒、単一スレッド)。Janome は 0.8 ms、GiNZA は約 20 ms(49 通/秒)。トークン比(o200k)は m 0.85、g 0.64、naive 0.48。ginza-d は主語補完で 0.99(節が増えるため削減にならない)。

**2. トークン削減はトークナイザ依存(容量・トークナイザ表)** 空白区切りの m は o200k では 15% 減だが、**Qwen3 のトークナイザでは 24% 増**、DeepSeek-V3 では 0%。空白なしの g は全トークナイザで 28〜35% 減と頑健(ただし可読性・LLM 精度は下がる、下記)。

**3. 情報保持(実験4、ルールベース判定)** Sudachi/MeCab/GiNZA の変種は状態(検討中・未決定・伝聞・可能性など)を 98% 復元し、非完了を「完了」と誤読した割合は 0%。Janome は希望(〜たい)で 69% と最も弱い。naive は状態を 4% しか保てない(助詞・助動詞を落とすため)。この判定は同じ規則系による自己採点なので、実際の読み取り精度は LLM 回答(実験2)で確認した。

**4. LLM エンドツーエンド(実験2, 全メモリを文脈に投入、各 40 問)** gemma-4-12b の正答率:

| N | L0 | sudachi-m | sudachi-p | ginza-d | sudachi-g | naive |
|---|---|---|---|---|---|---|
| 10 | 100% | 100% | 100% | 100% | 90% | 90% |
| 100 | 90% | 95% | 95% | 100% | 78% | 68% |
| 300 | 80% | 88% | 85% | 88% | 73% | 50% |
| 600 | 63% | 83% | 68% | 75% | 58% | 20% |

N=600 で sudachi-m の L0 に対する改善は符号検定で p=0.022(L1 のみ正解 11 問、L0 のみ正解 2 問)。**naive は N=300/600 で明確に悪化(p=0.004/0.001)**。それ以外の差(N≤300 の m/p/d)は有意でない(p>0.1)。N=600 のコールド TTFT は L0 116 s に対し m 104 s、g 92 s、naive 62 s。ginza-d はトークンが減らず 118 s。変換時間は書き込み時に 1 回払えばよく、1 件あたり約 0.05 ms なので TTFT 短縮に比べ無視できる。ただし L1 の利点が主にトークン削減によるもので、**精度向上**は長い文脈で L0 の読み落としが増えるぶんの差である可能性が高い(L0 は N=600 で 63% まで低下)。

qwen3-8b は短い文脈でも低精度(N=100: L0 53%、m 53%、p 63%、g 38%、naive 18%)。**Qwen3 のトークナイザでは m のトークンが L0 より 27% 増え、TTFT も 12.8 s → 16.2 s と悪化**した。精度の差は有意でなく(m 対 L0 p=1.0)、naive のみ有意に悪い(p=0.002)。

**5. RAG / メモリ検索(実験3)** クエリは原文のまま、検索は BM25 と 2 種の埋め込み(nomic-embed-text-v1.5、qwen3-embedding-0.6b)。メモリ 10,000 件での Recall@5:

| 表現 | BM25 | nomic | qwen3-emb |
|---|---|---|---|
| L0 | 0.72 | 0.52 | **0.94** |
| sudachi-m | 0.94 | 0.60 | 0.82 |
| sudachi-g | 0.94 | 0.58 | 0.85 |
| ginza-d | 0.99 | 0.65 | 0.82 |

BM25 は L1 化で大きく改善する(助詞・語尾のノイズが消え、氏名と述語が目立つ)。一方 **qwen3-embedding は L0 の方が強く、L1 化で下がる**(10,000 件で 0.94 → 0.82)。クエリも L1 化すると埋め込み検索ではむしろ悪化する(sudachi-g で 0.67)。naive は BM25 が原文クエリで 0.17 だがクエリも変換すると 1.00 になる。氏名と事象だけで正解を当てられるデータ設計のためで、**検索指標だけでは状態の保持は測れない**(実験4・2 と合わせて判断する)。

RAG モード(実験5, BM25 上位 5 件を LLM へ, 各 40 問): N=10,000 で L0 の正解取得率は 80%、sudachi-m は 95%、ginza-d は 100%。gemma の回答精度は L0 75%、m 78%、d 83%、g 65%、naive 65%。qwen3-8b は L0 75%、m 60%、d 65%、naive 23% と一貫せず、40 問では順位の入れ替えが誤差の範囲を超えない。RAG では絞り込み後のプロンプトが元々 200〜300 トークンなので、トークン削減による利点はほとんど出ない。

**6. 長文脈(10/100/1,000/5,000/10,000 件)** コンテキスト窓 19,456 トークンに全件が入るのは L0 で約 770 件、m で約 900 件、g で約 1,190 件、naive で約 1,610 件まで(1,000 件以上は RAG が必須)。5,000・10,000 件の検索はクエリ・解析・埋め込みを含めても L1 のコストは小さい。

**7. 損益分岐(実験6)** 変換コストも節約も文字数に比例するため、損益は文長の閾値ではなく prefill 速度で決まる。Sudachi/MeCab の m・g は、prefill 速度 20,000 tok/s までのどの条件でも**最初の 1 回の使用で変換コストを回収**する(R_be ≈ 0.0002〜0.59)。GiNZA-m は 100 tok/s で 0.39 回、ginza-d は節が増えてトークンが減らないため回収不能。メモリ件数・文脈長・LLM サイズでは分岐は動かず、効くのは変換器の速さと**トークナイザが L1 を短くするか**(Qwen3 では m は逆効果)。

**8. 埋め込み速度の再計測** 検索実行中の qwen3-embedding の計測は他モデルが常駐していて汚染されていたため、埋め込みモデルだけをロードして再計測した(`embed_retime.json`)。nomic は L0 81 件/s、L1 系 85〜88 件/s。qwen3-emb は L0 23 件/s に対し L1 系 15〜17 件/s と**遅くなる**(トークン数が増えるため)。

### 結論と限界

- 簡易 L1(解析器 + ルール)は**十分に安い**(1 通 0.05 ms)。Sudachi/MeCab の空白区切り m は、gemma-4-12b の全文投入(N=600)で L0 より正答率が高く、TTFT も短い。
- ただし**トークナイザと検索器に強く依存**する。Qwen3 のトークナイザでは m はトークンが増え TTFT も悪化。qwen3-embedding では L0 の方が検索精度も速度も良い。BM25 では L1 が有利。
- **助詞・助動詞まで落とす naive は不可**(状態情報が失われ、LLM 正答率が大幅に低下)。g(空白なし連結)は削減率は最大だが、LLM 精度が下がる。
- 限界: ①データは自作の会話体生成器で、実際の会話ログではない(氏名 + 事象でほぼ一意に引けるため検索は易しい)。②LLM の評価は各条件 40 問で、有意と言えるのは naive の悪化と gemma N=600 の m だけ。③情報保持(実験4)は規則による自己採点。④LLM は 2 モデル、埋め込みは 2 モデル、ハードウェアは 1 台(M 系 Mac)。⑤LLMLingua との比較は対象外。⑥N=10,000 の RAG は LLM に渡すのが BM25 上位 5 件(埋め込み検索を RAG の入力に使った場合は未評価)。

### #25 なぜ長文脈で L0 より高精度になるのか(トークン量 vs 意味密度)
N=600 メモリで、L0 / sudachi-m / **L0 を m のトークン数に縮めた L0-tm** / **m を L0 のトークン数に伸ばした m-tm** を比較(正解メモリは全条件に必ず含まれる)。質問を 2 サンプル(状態QA計 120 問)合算:

| 条件 | 正答率(95%CI) | L0 との差(L1のみ正解:L0のみ正解, p) |
|---|---|---|
| L0@600 | 67.5%(0.59-0.75) | |
| sudachi-m@600 | 75.0%(0.67-0.82) | 26:17, p=0.22 |
| L0-tm@534 | 70.8% | 12:8, p=0.50 |
| m-tm@674 | 70.8% | 22:18, p=0.64 |

N=300(120 問合算)は L0 77.5%、m 78.3%、L0-tm 76.7%、m-tm 78.3% で差なし(p=1.0)。N=100 も差なし。
- **#20 の「N=600 で m が +20pt(p=0.022)」は再現しなかった**。同じ質問サンプルでも別サンプルを足すと差は +7.5pt(p=0.22)に縮み、有意ではない。#20 の p 値の一部は偶然だった可能性が高い。

- qwen3-8b の再現は LM Studio が 4,000 トークン超で停止・文字化けしたため N=100 のみ(L0 57% / m 57% / L0-tm 57% / m-tm 53%、差なし)。Qwen3 のトークナイザでは m は L0 より 25% 長い。
- 時期QA は L1 が不利(例: N=600 で L0 95% / m 80%)。時間表現が落ちやすい。

### #30 圧縮限界・最小十分表現(gemma, N=300, L0 80%)
1 要素ずつ消す/残す ablation(28 条件、Pareto は `chart_pareto_google_gemma-4-12b.svg`):
- **削除しても壊れない(表層文法)**: フィラー(80%)、丁寧語(83%)、助詞(80%)、重複主語(ginza-d 80%)、文区切り(83%)、たい/う/らしい・みたい(83〜85%)。フィラー・丁寧語・助詞をまとめて消した surface-stripped は 85%(トークン 0.84)、さらに状態の標識を正規化した版は 88%(0.84)で、L0 を下回らない。活用形を残す m+conjugation も 87%。
- **壊れる(意味・関係)**: 状態標識を全部消す content-only 55%(p=0.004)、かも(不確実性)68%、ない(否定)73%、語順の逆転 27%、シャッフル 47%、主語(人名)の除去 37%。naive(ひらがな連の削除)は 35%。個別の標識の差は 60 問では有意でなく(p>0.1)、傾向として読む。
- 最初に壊れる意味カテゴリ: 否定と不確実性、その次に語順(係り受けの代替)と主語。
- **最小十分表現(経験的)**: 「内容語 + 状態標識(ない/た/かも)+ 語順 + 主語」を保ち、表層文法(助詞・丁寧語・フィラー)を落とした表現。トークン削減は gemma で 16%(0.84)、sudachi-g 相当の連結で 30%(0.70)まで精度を保てたが、後者は N=600 で崩れる(#20)。

### #26 Tokenizer-aware L1
同じ意味を、単語区切り(空白/なし/・/,)×文区切り×標識の書き方(かな/1漢字/ASCII)×活用語の表記(見出し語/かな)=96 通りで書き分け、tokenizer ごとにトークン最小のスタイルを選択(状態復元 97% 以上・完了への誤読 0 を制約。較正 400 件、held-out 600 件)。`tokaware.json`、`chart_tokaware_ratio.svg`:
- 汎用 m の L1/L0 は cl100k 0.84、o200k 0.84、**Qwen3 1.21**、gemma2 0.88、llama3.1 0.90、mistral-nemo 0.91、DeepSeek 0.98。トークナイザ別の最小スタイルは 0.59〜0.66 で、**語を区切らない連結形が全 tokenizer で最小**。
- 「単語区切りと文区切りを残す」読みやすさ制約をつけると 0.74〜0.89 で、Qwen3 では 1.03(削減なし)。トークナイザ別に探索するだけの利点は主に Qwen3 で大きい(m 1.21 → 最小 0.66 / 制約付き 1.03)。
- gemma QA(N=300): gemma 用の最小スタイル(0.67)は 83% で L0(80%)と同等、TTFT 57 → 41 秒(-28%)。汎用 g(0.70)は 75%、読みやすさ制約付き(0.86)は 70%。差は有意でない(p>0.28)。別の tokenizer(Qwen3)用に選んだスタイルでも 80%・0.67 で、**この条件では tokenizer 固有の最適化が精度や速度に与える差は検出できなかった**。
- qwen3-8b(N=100): 汎用 m はトークン +26%・TTFT 悪化(13.2 → 15.8 秒)、qwen 用最小スタイルは 0.72 で TTFT 9.4 秒(-29%)、精度は全条件 53〜65% で差なし。
- 設計指針: `compile_l1(text, target_tokenizer)`(`tokaware.py`)で、スタイル格子を較正セット上で全探索し、状態復元の制約を満たす最小を選ぶ。ただし精度制約は LLM でなくルールなので、**最終選択は LLM での QA 検証を必須**にする(連結形は長文脈で劣化する)。

| 表現 | トークン比 | 正答率 | L0 との差(p) |

| L0 | 1.00 | 82.9% | |
| sudachi-m | 0.69 | 71.1% | 2:11, p=0.022 |
| sudachi-g | 0.58 | 77.6% | 3:7, p=0.34 |

| refined-r1 | 0.78 | 80.3% | 2:4, p=0.69 |
| refined-r2 | 0.82 | 82.9% | 2:2, p=1.0 |

- 合成データと違い、**自然会話では汎用 m は有意に L0 を下回った**。失敗は否定(NOT_DONE 0.86 → 0.43)、言い直し(0.82 → 0.68)、俗語(0.94 → 0.71)、指示語(0.81 → 0.69)で、伝聞の「〜んだって」の「って」や口語の感動詞・接続詞が落ちていた。
- この分析から精製ルールを作った(refined-r1: 活用形・感動詞・接続詞・フィラー・伝聞の「って」を残す、r2: さらに格助詞と接続を残す)。r2 は L0 と同じ 82.9% でトークン -18%(TTFT 79 → 65 秒)。**精製は評価した同じ会話の失敗から作ったため過学習の可能性があり、別の会話セットでの検証は未実施**。
- 合成データの規則性が #20 の結果を過大評価していた可能性が高い。qwen3-8b は 4,000 トークン超の文脈で LM Studio が文字化けを返したため評価できなかった。

### #28 L0/L1 Dual-Index RAG(メモリ 10,000 件・300 クエリ)
BM25 は L1 側(語彙)、ベクトルは L0 側(意味)で融合(RRF k=60、重み付きの重みは開発クエリで選択)。Recall@5(MRR):

| 方式 | nomic | qwen3-embedding |
|---|---|---|
| BM25(L0) | 0.76(0.61) | 同左 |
| BM25(L1) | 0.93(0.87) | 同左 |
| Vector(L0) | 0.55(0.42) | 0.93(0.85) |
| Vector(L1) | 0.58(0.42) | 0.77(0.76) |
| Hybrid(L0 のみ) | 0.85(0.60) | 0.94(0.80) |
| **Dual = BM25(L1)+Vector(L0)** | 0.82(0.62) | **0.97(0.90)** |
| Dual + 2-view クエリ | 0.82(0.64) | 0.99(0.92) |
| 重み付き Dual | 0.93(0.87)(重み 0.9) | 0.98(0.93)(重み 0.6) |

- **qwen3-embedding(semantic が強い)では Dual が最良**(2-view で R@5 0.99)。nomic(semantic が弱い)では BM25(L1)単独が最良で、融合はむしろ下げる。**相補性は semantic 側が十分強いときだけ成立する**。
- BM25(L1)は L0 の 1/4 のクエリ時間(14.6 vs 56 ms)、転置索引 45% 減(ポスティング 8.7 万 vs 15.7 万)、テキスト 38% 減(59 万 vs 94 万 B)。qwen3-embedding のクエリ埋め込みは 29 ms 追加。
- 再ランカー: 使える cross-encoder がなく「BM25(L1)上位 50 件を Vector(L0) で並べ替え」で代用(qwen3 で 0.93、Dual に及ばず)。LLM 再ランカーは未実施。
- 最終QA(gemma, 上位 5 件, 60 問): Dual で L0 を渡すと 95%(取得ヒット率 98%)、BM25(L0) は 73%(同 73%)。Hybrid(L0 のみ)・quad も 95% で、**最終精度では Dual の優位は示せない**。LLM に L1 を渡すと精度が下がる(Dual 88%、Vector 80%)ので、**検索は L1、LLM への入力は元の L0** が妥当。

### #31 多言語パーサベース L1(Semantic Density Convergence)
同じ事実 600 件(人物×12 出来事×7 状態×時期)を日・英・韓・中でテンプレート描画し、言語ごとの既存解析器(ja SudachiPy、ko Kiwi、zh jieba、en spaCy の lookup 見出し語化+機能語表。**統計タガーが取得できなかったため英語は規則ベース**)で決定的に L1 化(LLM なし)。
- **トークン**: tok/fact の言語間 CV(平均の標準偏差/平均)は 7 トークナイザすべてで L1 < L0(例: o200k 0.189 → 0.118、gemma2 0.312 → 0.116、事実のブートストラップで P(CV L1<L0)=1.00)。マーカーを全言語で同じ ASCII にしても、標識を全部消した content-only でも 6/7 で成立(mistral-nemo のみ悪化)。事実ごとの言語間 CV も 7/7 で低下。**ただし言語は 4 つで、CI は事実のリサンプリングのみ(言語の標本不足は扱えない)。素材は構造が揃ったテンプレートで、実際の文での収束は未検証**。
- **QA(gemma, N=300, 60 問)**: 収束してもQA は保てない。L0 → L1 → L1n(標識を各言語の語で表記): 日 70% → 68%、英 90% → 73% → 85%、韓 70% → 57% → 45%、中 90% → 40% → 72%。中国語 L1 は文字数が逆に増え(10.4 → 13.9 字)、ASCII ラベルの可能性・未決定が壊れた(0/11、0/8)。ネイティブ語のマーカーにすると中国語・英語は大きく回復するが、韓国語は悪化した(伝聞 1/13)。
- 結論: 「言語ごとの決定的 L1 で tok/fact は収束する」は支持されるが、**収束した表現が意味を保つ(最小十分表現になる)ことは言語・マーカー設計に依存**し、日本語以外では未達。#21(7 言語)は本件の拡張として残る。

### #29 Transformer は L0 と L1 をどう読んでいるか
動かせる唯一のオープンウェイトの小型モデル Qwen3-1.7B(MLX 4bit)で、最終トークンの層ごと・ヘッドごとの注意、隠れ状態、正解logit余裕を記録(N=100/250、正解位置 5 通り、条件は L0/m/g と、L0 を m・g のトークン数に調整した L0-tm)。`attn*.json`(隠れ状態の配列 `*_hidden.npz` は 137 MB のため未コミット。`python -m machine_kanbun.jpattn 100 8 attn` で再生成):
- このモデルは課題を解けない(正答率 0.23〜0.45。4 択のランダムは 0.25)ため、**L0 と L1 の差を内部表現から検出できなかった**。最終トークンの注意は質問・指示部(約 39%)と先頭(約 55%、attention sink)に集中し、正解メモリは条件によらず 0.1〜0.3% だった。人名・出来事・状態トークンへの注意量にも L0/L1 差はなかった(1 つのヘッドの最大でも正解メモリへ約 1%、0.009〜0.014)。なお m の人名スパンは姓名の間に空白が入って文字列一致で取れず欠損(nan)で、注釈の限界。
- N=250 の位置別: **メモリの中央(位置 0.5)で正答率が全条件で 0.00**(先頭・末尾は 0.25〜0.75)で、lost-in-the-middle が出ている。L1(m・g)でも同じで、軽減は確認できない。
- 隠れ状態の最終層 cosine(L0 との類似)は 0.96〜0.99。L1 は L0-tm より少し離れる(0.96 vs 0.99)が、小さな変化。正解メモリへの注意量と正解logit余裕の相関はプロンプト単位で -0.1〜+0.5(n=20〜80 で不安定)。
- 結論: 仮説(L1 で重要トークンへの注意が集中する)は、このモデルでは検証不能。より大きい(かつ注意を取り出せる)モデルが必要。

### 限界
- 評価 60 問/条件(合算で 120)では、数ポイントの差は有意にならない。多重比較の補正はしていない。
- #20 の結果の一部(N=600 の優位)は再現せず、データの規則性・質問サンプルへの依存が大きい。
- 自然会話は LLM 生成で、gemma 自身が読める会話に絞っているため L0 に有利。精製L1 は同じデータからの学習で過学習の可能性。
- qwen3-8b は LM Studio が長い文脈で不安定なため N=100 のみ。MLX 解析は小型モデルのみ。
- 英語パーサは規則ベース、言語は 4 つ。7 言語(#21)は未実施。
