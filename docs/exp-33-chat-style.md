# Issue #33: SCF 圧縮 Chat 履歴は日本語回答の文体を汚染するか

[← README に戻る](../README.md) ・ [用語(NF/SCF/SeCF)](terminology.md)

NF(原文)の古い会話履歴を SCF(sudachi-m = SCF-L1)にして文脈に入れたとき、回答が SCF 風の電報文体に引っ張られないかを測る。`jpchat.py`(シナリオ・条件・文体指標・採点)、`jpchatreport.py`、`scripts/run_jp3*.sh`、結果は短い履歴が [results/jp3/report.md](../results/jp3/report.md)・`results.csv`・`chart_l1_ratio.svg`、長い履歴(24 往復)が [results/jp3/long_report.md](../results/jp3/long_report.md)・`long_results.csv`・`chart_long_l1_ratio.svg`。

**設計**: 8 往復のチャット(友人の話。目標人物の状態 7 種 × 各 5 = 35 シナリオ。目標の事実は最も古い往復に置く)。assistant 側の古い返事は gemma-4-12b が NF 履歴から生成(敬体の persona)。最後のユーザー発話は常に NF の「{人物}さんにどう声をかけたらいいかな？」。回答は gemma-4-12b(温度 0)、**条件を伏せた採点は別モデルの qwen3-8b**(自然さ・意味保持・会話らしさ・SCF 文体汚染、各 1〜5)。加えて回答の形態素統計(助詞率・平均文長・名詞/動詞率・文末表現率・体言止め率・敬体率・電報文率・SCF 記号/「/」)、トークン、TTFT、変換時間。

条件(15): **A** 全 NF(メッセージ列)、**B_c{2,4,6,7,8}** 古い c 往復を SCF にしたメッセージ列(c=8 が全履歴 SCF、SCF 比率 25〜100%・直近 NF 窓 6〜0 往復)、**D_c{2,4,6,7,8}** 圧縮部を `<compressed_context>` に分離し英文の分離指示(「文体を真似しない」)を付けたもの、**T0** D と同じ構造・指示で古い履歴を NF のままにした構造の対照、**D0** D で指示なし、**P2/P3** 配置の違い(直近 NF → SCF ブロック → 質問、ブロック直後に persona と文体注意)。

**結果(短い履歴、35 件 × 15 条件、`results/jp3/report.md`)**
- **文体の汚染は検出されなかった**: 自然さ 4.89〜5.00(baseline 4.94)、SCF 文体汚染 1.14〜1.34(baseline 1.34)で、全 14 条件で baseline との差は有意でない(p≥0.06)。電報文率は 0.000〜0.010、「未」「有」の模倣は 0、「/」の混入もほぼ 0。意味保持も 4.60〜4.80(baseline 4.63)。**ただし採点は天井(5 付近)に近く、差を拾う力が弱い**。
- **SCF 比率と体言止め**: メッセージ列方式で c を増やすと体言止め率が 0.06 → 0.13(c=7)、文末表現率が 0.87 → 0.70、平均文長が 34.6 → 26.5 字、敬体率が 0.47 → 0.42 に動く(c=8 では 0.11 / 0.76 / 28.4 / 0.46 に戻る)。単調ではなく、電報文体には至らない軽い drift。
- **分離+指示(D)**: 敬体率が 0.58〜0.67 に上がり、汚染が 1.14〜1.26 とやや低い。ただし **T0(古い履歴は NF のまま)でも同じ**(敬体率 0.62、汚染 1.26)なので、効果の大半は SCF 化の影響ではなく**構造と指示そのもの**による(回答も 539 → 約 300〜420 字に短くなる)。配置(P2/P3)で汚染は増えない(1.17)。
- **事実の使われ方(補助指標)**: 回答が目標の出来事に言及した割合は、baseline 0.60 に対しメッセージ列の c=8 で 0.69、分離方式の c=8 で 0.74(差は有意でない、p≥0.27)。圧縮した履歴からも事実は取り出せていて、減ってはいない。UNDECIDED の例では、メッセージ列方式は「元気がない」だけに触れ、分離方式は「手術を迷っている」まで踏まえた。採点の意味保持は寛容で(一般論は誤りにならない)、この差を拾えていない。
- **圧縮**: この短い会話(約 410 トークン)ではメッセージ列方式で 0.89〜0.97、分離方式は英文の枠指示のコストで 1.02〜1.10(指示なしの D0 で 0.98)。**「トークンを有意に削減」の成功条件は短い履歴では満たせない**(長い履歴の結果は次節)。
- 成功条件の判定(意味保持・自然さ・汚染・敬体率・圧縮率 < 0.95)は、メッセージ列方式の c=4〜8 が満たし、分離方式は圧縮率で満たさない。

- **文体汚染は長い履歴でも検出されない**: 自然さ 4.81〜5.00、汚染 1.00〜1.38、会話らしさ 4.90〜5.00 で、baseline との差はすべて有意でない(p≥0.12)。電報文率は 0.000〜0.004、記号の模倣は 0。
- **圧縮は小さい**: 全履歴 SCF で 0.89(-11%)、古い 2/3 で 0.92〜0.93。この履歴は assistant の返事が丁寧で長く、SCF にしても削れる量に限りがある(NF 履歴の文字数の約 6 割を assistant の返事が占める)。**「トークンを有意に削減」は小さな削減(約 7〜11%)にとどまる**。分離方式の枠指示のコストは長い履歴では吸収され(0.89〜0.93)、短い履歴のように増えない。
- **メッセージ列方式で全履歴を SCF にすると体言止めが 0.03 → 0.11、文末表現率 0.94 → 0.79、平均文長 39.2 → 29.5 字、敬体率 0.57 → 0.47** と軽い文体の drift が出る(短い履歴の c=7〜8 と同じ傾向)。分離+指示(D_c24)ではこの drift が小さい(体言止め 0.02、敬体率 0.63)。ただし T0 でも体言止めは 0.00・敬体率は 0.70 で、**分離方式の効果の大半は構造と指示そのもの**による点は短い履歴と同じ。
- **目標の事実の使われ方は SCF 履歴のほうが良い**: 回答が目標の出来事に言及した割合は baseline 0.38 に対し 0.57〜0.76(D_c24 は +0.38、p=0.008。他は p≥0.11。多重比較の補正なし)。古い履歴を圧縮して短くしたほうが、モデルが古い事実を参照しやすくなる傾向がある(#25 のトークン削減・文脈長の議論と整合するが、この規模では確証ではない)。UNDECIDED の例では、baseline は一般論の声かけにとどまり、SCF 履歴の回答は「手術を迷っている」状況を踏まえた。
- 成功条件の判定: B_c16・D_c16・D_c24・P2 が満たし、B_c24 は敬体率の低下(-0.10)で満たさない。

## 結論(Issue の問いへの回答)
- **L1(SCF)で文脈を持ち、NF で話すことは可能**: 古い履歴を SCF にしても、直近の質問が NF であれば回答の自然さ・会話らしさ・persona(敬体)はほぼ維持され、電報文体の混入は検出されなかった(短い履歴 35 件、長い履歴 21 件)。
- **どこまで SCF 化できるか**: 全履歴(100%)まで SCF 化しても自然さは落ちない。軽い drift(体言止めの増加、敬体率の低下)は SCF 比率が高いメッセージ列方式で出るが、分離方式では小さい。直近 NF 窓は 0 往復でも問題が出なかった(必要な最小窓は、この条件では 0〜2 往復と見られるが、差を検出できる規模ではない)。
- **配置**: SCF ブロックを質問の近くに置いても(P2)、汚染は増えない(1.17 / 1.33)。短い履歴では差なし、長い履歴では意味保持が 4.43 とやや低い(p=0.125、有意でない)。
- **分離指示は有効か**: 敬体率と体言止めは改善するが、構造だけ(T0)でも同じ程度に改善するため、**SCF 汚染を抑える効果としては示せない**(そもそも汚染が小さい)。
- **トレードオフ**: トークン削減は 7〜11% と小さい。この会話(assistant の返事が長い)では、SCF 化の利点は主に「古い事実を参照されやすくなる」ことで、圧縮そのものではない。

**限界**: 回答は gemma-4-12b 1 モデル、採点は qwen3-8b 1 モデル(LLM 採点の天井効果。人手の匿名評価は未実施で、`results/jp3/blind_sheet.csv`・`long_blind_sheet.csv`(各 80 件)と鍵 `blind_key.csv` を用意した)。長い履歴は 21 シナリオで検出力が低い。シナリオは合成(テンプレートの発話 + gemma の返事)で、実際の長時間チャットではない。温度 0 の 1 回生成で、生成のばらつきは見ていない。

## (初回)構造化 SeCF 条件 — **SeCF-L5 相当であり、SeCF-L1 の結果ではない**(同じ 35 シナリオ・8 往復、13 条件。`results/jp3/secf_report.md`)
> **訂正(2026-10-06)**: この節の「SeCF」は `主体{event:..; state:..}` 型の構造化表現で、#19 の分類では SeCF-L5 相当(構造化 IR)。#33 が比較すべき SeCF-L1 は #19 の L1(簡潔な自然言語)で、その結果は後ろの「SeCF-L1 での再実行」を正とする。この節は研究履歴として残す。
古い履歴の各発話(user・assistant とも)を gemma-4-12b(温度 0)が `主体{時:..; event:..; state:..; decision:..}` 形式の意味構造(SeCF)に変換した(`jpchat.secf_text`、キャッシュ `secf_cache.jsonl`、420 発話)。条件は SCF 側と対応: **C_c{2,4,6,7,8}**(メッセージ列、c=8 が E の全履歴 SeCF)、**G_c{2,4,6,7,8}**(`<compressed_context>` に分離+指示)、**G0**(指示なし)、**GP2/GP3**(配置)。A_base・T0 と SCF 条件(B・D・P2・P3)は既存の結果を使う。回答は gemma、匿名採点は qwen3-8b で SCF と同一。SeCF 固有の指標として、構造記号(`{ } [ ] ;`、`key:`)・箇条書き行率・field 名(event/state/decision/アシスタント{ 等)の混入を追加した。実行は `scripts/run_jp3_secf.sh`。

- **SeCF でも文体・構造の汚染は検出されなかった(H1〜H4 はこの規模では支持されない)**: 自然さ 4.83〜5.00(baseline 4.94)、会話らしさ 4.89〜5.00。構造記号は 0.00〜0.01/100 字、field 名の漏出は最大 0.02/100 字(C_c4)で、JSON 風・データ構造の回答は見られなかった。汚染スコアは SCF 条件と同程度かやや低く(C_c6 1.06、p=0.004、C_c8 1.11、p=0.021。ただし baseline より**良い**方向で、多重比較の補正なし、採点は天井近く)、SeCF が SCF より汚染を増やす証拠はない。H4(中間の SCF で最大になる非単調性)は、SCF 自体が汚染を起こさなかったため検証できない。
- **トークンは SeCF のほうが増える**: メッセージ列方式で 1.03〜1.10(c=2〜8)、分離方式で 1.19〜1.27(英文の枠指示を含む)、GP3 は 1.35。SCF は 0.89〜0.97(メッセージ列)で、**この会話では SeCF は圧縮にならない**。波括弧・フィールド名・記号で日本語トークンが増えるため。
- **直近 NF の窓と比率**: SeCF のメッセージ列は敬体率 0.45〜0.54(baseline 0.47)で、SCF のような低下(c=7 で 0.42)は小さい。分離方式は SCF と同様に 0.63〜0.67 で、T0(構造だけ、0.62)と同程度なので効果は構造と指示に由来する。窓 0 往復でも問題は出なかった。
- **配置・指示**: GP2/GP3/G0 でも汚染は増えない(1.23)。指示の有無で差はない。
- **意味保持**: C 条件は 4.74〜4.94 で baseline(4.63)以上。目標の出来事への言及率は C_c6〜c8 で 0.40(baseline 0.29、有意差の検定は未実施・差は小さい)。変換でモダリティ(迷い・伝聞)が落ちる例もあり(C_c8 の UNDECIDED の回答は手術に触れていない)、採点の天井のため差を拾えていない。
- **変換コスト**: SeCF は 1 発話あたり平均 1.5 秒(LLM 推論)。SCF の sudachi-m は 1 ms 未満で、約 1,000 倍。

**結論の追加(構造化 SeCF(L5 相当)について。SeCF-L1 の結論ではない)**: この条件(gemma-4-12b、合成の 8 往復、LLM 採点)では、どちらの形式でも NF で話す回答の自然さ・persona は保たれ、SeCF のほうが構造汚染を起こす証拠も出なかった。差が出るのは**コスト側**で、SCF は圧縮率 0.89〜0.97・変換 1 ms 未満、SeCF は 1.03〜1.27・変換約 1.5 秒。よって Chat の履歴表現としては、トークンも変換コストも有利な **SCF が実用的**で、SeCF はこの用途では利点を示せなかった(長期記憶など別用途での価値は別問題)。限界は SCF 側と同じ(1 モデル、LLM 採点の天井効果、合成データ、1 回生成)。SeCF の変換は LLM 1 モデル・1 つのプロンプトで、別の SeCF 設計(より短い記法など)では圧縮率が変わりうる。

## 追補(Issue #49): 圧縮履歴からの古い事実の想起は NF より悪い — 上の「事実の使われ方」は取り下げ
`jpchatqa.py`、`jpchatqareport.py`、`scripts/run_qa49.sh`、結果は [results/jp3/qa_report.md](../results/jp3/qa_report.md)・`qa_results.csv`。同じ履歴(短 35 件、長 21 件)の最後に、目標人物の状態を 7 択(DONE/NOT_DONE/PLANNED/WANTED/UNDECIDED/HEARSAY/POSSIBLE の文)で問い、記号 1 文字の一致で**決定的に採点**した(選択肢の並びを 3 通りに入れ替えて平均、gemma 温度 0、ランダム 14%)。N = NF の履歴から**目標人物に関係しない往復を落として** o200k の大きさを SCF にそろえた対照。

| 条件 | 短い履歴 正答率(圧縮率) | 長い履歴 正答率(圧縮率) |
|---|---|---|
| A 全 NF | 0.971 (1.00) | 1.000 (1.00) |
| N トークン一致 NF | 0.971 (0.91) | 1.000 (0.90) |
| B 全 SCF(メッセージ列) | 0.867 (0.92)、vs A -10.5pt p=0.027 | 0.825 (0.90)、-17.5pt p=0.063 |
| D SCF 分離+指示 | 0.924 (1.02)、-4.8pt p=0.37 | 0.937 (0.91)、-6.3pt p=0.13 |
| E 全 構造化(SeCF-L5 相当、メッセージ列) | 0.819 (1.08)、-15.2pt p=0.029 | 0.730 (1.12)、-27.0pt p=0.004 |
| G 構造化(SeCF-L5 相当)分離+指示 | 0.724 (1.20)、-24.8pt p=0.003 | 0.698 (1.15)、-30.2pt p=0.004 |

- **H1(トークン仮説)・H2(密度仮説)は否定、H3(損失仮説)を支持**: 圧縮で正答率が下がり(SCF -10〜-17pt、SeCF -15〜-30pt)、トークン数をそろえた NF は NF と同じ(97〜100%)。SCF/SeCF の利点は「古い事実が参照されやすい」ではなく、**むしろ状態の取り違えが増える**。
- **何が落ちるか**: SCF は WANTED(長 1.00 → 0.33)と DONE(長 → 0.56)、誤りの行き先は HEARSAY が多い。`中島麻衣さんは入院したがっている` → `いう 中島 麻衣 入院 たい`、`始めました` → `始める た` のように、助動詞(たい・た)が単独の断片として残り、願望・完了の区別が曖昧になる(#30 の「状態標識を残す」は否定・不確実性が中心で、願望・完了は対象外だった)。SeCF は NOT_DONE が崩れる(短 0.33、長 0.22。NF は 1.00)。NOT_DONE→UNDECIDED・POSSIBLE・HEARSAY に流れる。モダリティ系 4 状態の正答率は SeCF 0.83(短)/0.75(長)で NF 1.00 より 17〜25pt 低い(成功条件 H3 の ≥10pt を満たす)。
- **分離+指示は SCF では緩和する**(B -10.5/-17.5pt → D -4.8/-6.3pt、有意でない)が、**SeCF では悪化する**(E → G で -9〜-3pt、トークンも 1.15〜1.20 倍)。
- **上の「事実の使われ方(補助指標)」と「目標の事実の使われ方は SCF 履歴のほうが良い」は取り下げる**: 語の有無のヒューリスティックでは圧縮履歴のほうが言及が増えたが、正答率では逆転した。言及の増加は事実が**正しく使われた**ことを意味せず、誤った状態の言及(例: 願望を「予定」として扱う)を含んでいたと考えられる。#33 の「SCF は Chat の履歴表現として実用的」は、**文体の軸では成立するが、正確さの軸では状態の取り違えのコストがある**と読み替える。
- **限界**: N は「無関係な往復を落とす」ので、どの往復が無関係かを知っている強い対照(実運用では使えない)。圧縮率は 0.90〜1.20 と幅が狭い。回答は gemma 1 モデル、状態は 7 種の合成事実、履歴は合成、選択式(自由回答ではない)。SCF の変換器は #20 の簡易 L1(sudachi-m)で、願望・完了の助動詞を標識に置き換えれば改善する可能性がある(未検証)。

## 追補(Issue #51): 標識に凡例・自明語を付けても SCF の想起低下は回復しない
#49 の QA(同じ 56 シナリオ・3 通りの並び・決定的採点)に、B(全 SCF、メッセージ列)の変種を 3 つ足した。**B_legend**: システムプロンプトに標識の凡例(た=過去・完了、たい=願望、ない=否定、らしい=伝聞、かも=可能性、みたい=推量)を追加。**B_expl**: 標識を自明語に置換(た→済、たい→希望、ない→否定、らしい→伝聞、かも→可能性、みたい→推量。`jpchat.l1_expl`)。**B_expl_legend**: 両方。`scripts/run_qa51.sh`、結果は [results/jp3/qa_report.md](../results/jp3/qa_report.md)。

- **H1(凡例仮説): 方向は正だが成功条件を満たさない**: 凡例で B より +4.8〜+6.7pt 高いが有意でなく(p=0.20、0.50)、短い履歴ではトークンが 1.01 倍で圧縮にならない(長い履歴は 0.94)。A との差は短 -3.8pt(有意でない)、長 -12.7pt(p=0.125)。**検出力不足で、効果がないとは言えない**(35/21 シナリオ)。
- **H2(自明語仮説): 支持されない**: 自明語への置換は B と変わらない(-2.9 / +0.0pt)。置換で DONE は回復する(短 0.80 → 1.00、長 0.56 → 1.00)一方、UNDECIDED(1.00 → 0.67、長 0.56)と HEARSAY(1.00 → 0.67)が崩れ、**誤りが別の状態に移るだけ**。
- **WANTED はどの変種でも回復しない**(長 0.33〜0.44、A 1.00): 標識を「希望」と明示しても、PLANNED や HEARSAY との区別が付かない。原因は標識の読みにくさだけではなく、`いう`・助詞・活用が落ちたことによる文構造の曖昧さ(H3)が残ると読める。
- **分離+指示(D)のほうが標識の工夫より改善が大きい傾向**(+5.7 / +11.1pt、有意でない)。構造と指示のどちらが効くかは #33 の T0 と同様に切り分けていない。
- **結論**: SCF の想起低下(-10〜-17pt)は、凡例や標識語の置換では**検出できる大きさでは回復しない**。標識の設計を直しても、状態保持の損失は残る可能性が高い。助詞・活用の削除そのものが願望・予定・伝聞の区別を損なう。#30 の「最小十分表現」には、否定・不確実性に加え**願望(たい)・完了(た)の区別と、それを保つ文構造**が必要という修正が要る(この実験で直接測ったわけではなく、WANTED の回復しなさからの推論)。**限界**: 検出力が低い(各条件 35/21 シナリオ、符号反転の置換検定、補正なし)、1 モデル、合成事実、選択式。

## 追補(Issue #54): 三層・二層の履歴(最古 SeCF-L1 / 中間 SCF-L1 / 直近 NF)

- **H1(両立仮説)は支持**: T3 は SeCF-L1 一本との想起の差が +2.9 / -1.6pt(有意でない)、NF との差も長で -4.8pt(基準 -5pt 以内)、圧縮率 0.92 / 0.90(≤0.92)、同期変換は SCF 部分だけで 14〜86 ms。SeCF 部分の変換(短で 8 往復 × 1 往復 約 2.5 秒 = 約 20 秒のうち古い半分)は非同期に回せる。**ただし圧縮率は SeCF-L1 一本(0.88 / 0.85)より悪い**。直近 1/4 を NF に戻した分のトークンが増えるため(T2 も 0.91 / 0.88)。**中間の SCF 層は、この構成では想起もトークンも T2 に対して上積みがない**(T3 と T2 の差は +2.8 / -3.2pt、有意でない)。
- **H2(混在悪化仮説)は否定**: T3 と T2 は SeCF-L1 一本・NF から悪化していない。異なる表現の混在そのものは想起を損なわなかった。
- **H3(中間層が弱点)は、目標の事実が SCF 層に入ると想起が落ちる点で、長い履歴では方向が支持**: T3m は T3 より短 -5.7pt(p=0.107)、長 -15.9pt(p=0.148)で、NF との差は長 -20.6pt(p=0.015、補正なし)。長 T3m の状態別: DONE 0.44、WANTED 0.44(B と同じ弱点)。短では差が小さく成功条件(≥10pt)に届かない。検出力不足で断定はできない。**SCF 層の想起の損失は、混在でも変わらず、どの往復が SCF 層に入るかで決まる**。
- **運用上の含意**: 「SCF-L1 で同期的に圧縮し、SeCF-L1 に非同期で置き換える」は、**SCF-L1 を「SeCF-L1 に書き直し済みでない最近の往復のつなぎ(暫定)」にとどめ**、書き直しが済んだら SeCF-L1 に置き換える運用なら想起を保てる。重要な事実がまだ SCF のままの往復に含まれる間は想起が落ちる(T3m)ので、**重要度の高い往復(状態を述べた往復)から優先して SeCF-L1 に書き直す**のが要点になる(この優先順位づけ自体は未検証)。
- **限界**: 層の割り当ては往復の位置で固定(実運用の重要度推定ではない)。短 35 / 長 21 シナリオ、選択式 QA、gemma 1 モデル、多重比較の補正なし。T3m の長は SCF 層に 6 往復が入る(短は 2 往復)ため、短と長で SCF 層の割合が違う(短 1/4、長 1/4 だが目標往復の数は同じ 2)。SeCF-L1 の非同期変換を実際に回したときの遅延・失敗は測っていない(変換時間 1.24 秒/発話の積算のみ)。
